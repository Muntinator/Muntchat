# Contributing to CalcGPT 3

Contributions are welcome, especially changes that can be measured on a real
TI-Nspire CX II instead of only improving desktop training loss.

Current version is 3.1. The model weights are still the E40 checkpoint and the
on-calculator data format is still 13, with model id 1282619148. `MODIFICATIONS.txt`
records everything 3.1 changed and why.

## Before changing code

1. Preserve the current E40 checkpoint and ready-to-run TNS.
2. Create a new checkpoint format number for incompatible architecture changes.
3. Keep calculator runtime code compatible with TI Python, not merely CPython.
   The desktop simulator does not model TI-Python limits.
4. Do not add canned conversational responses and describe them as understanding.
5. Do not claim classifier confidence is response accuracy.
6. Do not change the model id, the association/intent/emotion item caps, or the
   data format number unless you are deliberately making old installs
   incompatible. The model id is a CRC-32 over the weight blobs plus the
   association, intent and emotion blobs, so innocuous-looking table changes
   silently break it.

## Useful contribution areas

- A compact learned candidate ranker (the largest remaining gap)
- Teacher-student distillation focused on response relevance
- Subword or byte tokenization experiments
- Lower-memory loading and shorter first-response load time
- Stronger incomplete-sentence and repetition detection
- Extending or replacing the weighted bag-of-words conversation context
- UI, keyboard, scrolling, and paste bug fixes
- TI-Nspire OS and hardware compatibility testing

Already done in 3.1, so less useful as-is: the fixed held-out evaluation suite,
deterministic seeds and desktop benchmarks, faster matrix operations, resumable
checksummed installers, and basic conversation conditioning. See
`IMPROVEMENT_ROADMAP.txt` for the current status of each item.

## Testing expectations

The desktop suite is required. It runs the real generated calculator code against
a simulated `ti_system`/`ti_draw`, so it needs no calculator:

```
cd source
python3 -m venv .venv-test
.venv-test/bin/python -m pip install -r requirements.txt
.venv-test/bin/python -m unittest discover -s tests -v
```

A change that touches `calculator_template.py`, `export_calculator.py` or
`train_mac.py` is not ready until that suite passes (51 tests at the time of
writing) and you report before/after numbers:

```
.venv-test/bin/python tests/evaluate.py --label yours     # speed + quality
.venv-test/bin/python tests/run_suite.py --template PATH/tinylm.py \
    --data PATH/tinydata*.py --label yours                 # same prompts, same seeds
```

Keep `tests/results/` recordings for your build. If your change touches the model
format or the association builder, also run `tests/assoc_experiment.py` and
report held-out top-3 retrieval. Note that several plausible-sounding changes have
already been measured and rejected (contrastive PMI/TF-IDF association features,
larger association tables, always generating two candidates, stricter candidate
gates); check `MODIFICATIONS.txt` section 6 before repeating them.

## Changing the ready-to-run .tns

`build_tns.py` replaces the plain-text Python pages in an existing document and
copies TI's encrypted `Document.xml` / `Problem1.xml` byte-for-byte. It
deliberately never decodes or re-encodes TI's method 13 compression, and it
refuses to add a page that does not already exist in the base document.

Because of that, if a change needs a new Python page (for example the numbered
`tinydata2`..`tinydata8` installers), add it by hand in TI-Nspire Student Software,
use that updated document as `--base`, and rebuild. `tests/test_tns.py` asserts
that the committed document matches a fresh build, so a stale `.tns` fails the
suite.

After changing the runtime, re-run the end-to-end document check:

```
.venv-test/bin/python tests/verify_tns.py ../ready_to_run/CalcGPT3_v3.1.tns
```

This decodes the built document, recovers the model stored inside it, and runs the
runtime page the document actually ships. It needs `pycryptodome`, which is in
`requirements.txt` for exactly this purpose.

Never hand-edit a `.tns`. Never re-encode method 13 payloads.

Also record for hardware runs:

- Commit/version and checkpoint epoch
- TI-Nspire model and OS version
- Physical calculator or official preview
- Launch, first-load, and response timing
- Training and validation loss
- The complete standardized prompt suite
- Every output, including failures
- Peak document size and any MemoryError

Do not select only successful conversations. Compare the new version with the
included E40 model using the same prompts and random-seed policy.

Changing anything under `source/calculator_template.py` changes the shipped
runtime, so `source/calculator/tinylm.py` must be regenerated by
`export_calculator.py` and the regenerated files committed alongside the source
change. Never edit `source/calculator/tinylm.py` by hand.

## Bug reports

Copy `BUG_REPORT_TEMPLATE.txt` into your report and fill in every applicable
field. Include the entire traceback as plain text when possible.

## Pull requests or release forks

Keep generated artifacts separate from source. Do not commit `.venv`, downloaded
corpora, `.DS_Store`, `__MACOSX`, `__pycache__`, or every epoch snapshot. Include
only the active checkpoint when a trained model is necessary for reproduction.

`source/tests/ti_tns/` is third-party code vendored from the MIT-licensed
TnsTools project, used only to decode a `.tns` for verification. Do not edit it;
update it by replacing the files from upstream and keeping the `LICENSE` and the
provenance note in `__init__.py`.

Code contributions are accepted under the MIT License. Do not add datasets or
weights whose licenses are incompatible with the existing noncommercial release.
